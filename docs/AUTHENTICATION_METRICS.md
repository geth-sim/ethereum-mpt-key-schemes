# Authentication metric definitions

These measurements support the text in §5.3.1 (myHash, child pointers, cache
hits, and node reads) and the node-count-based estimates in §5.3.2. Figure 8
itself uses the existing **fast timing cases**, not the counter cases below.

## Measurement cases and commands

For each of `PVstar` and `VPstar`, E3 now includes:

| Case suffix | Configuration | Read-count baseline |
|---|---|---|
| `_counters` | No myHash, no myHash cache | This case |
| `_myhash_counters` | myHash, no myHash cache | Matching scheme's `_counters` |
| `_myhash_cache4g_counters` | myHash, unified 4 GiB cache | Matching scheme's `_counters` |

All six cases use the stats LevelDB binary and enable the existing
`--child-stats` and `--accurate-read-counters` options. These options disable
parallel hashing; their elapsed times are not comparable to the fast timing
runs. Both the baseline and its variants use the same counter configuration.
The manifest records these options and the runner records their effective
values under `resolved` in the run report.

After preparing MariaDB, run an individual case:

```bash
./scripts/run_paper_experiment.sh E3 validation E3_PVstar_myhash_cache4g_counters
python3 analysis/extract_auth_metrics.py \
  runtime/paper-experiments/validation/E3/run-report_E3_PVstar_myhash_cache4g_counters.json
```

For the total-node-read ratio, also supply its baseline report:

```bash
./scripts/run_paper_experiment.sh E3 validation E3_PVstar_counters
python3 analysis/extract_auth_metrics.py \
  runtime/paper-experiments/validation/E3/run-report_E3_PVstar_counters.json \
  runtime/paper-experiments/validation/E3/run-report_E3_PVstar_myhash_cache4g_counters.json \
  --output-dir runtime/paper-experiments/validation/E3/auth-metrics
```

Running the whole E3 family also runs the counter cases. In that case pass
the combined `E3/run-report.json`; do not also pass individual reports for the
same case. The extractor rejects duplicate case IDs.

For a paper-scale run, prepare the 10M input and replace `validation` with
`paper` in the execution commands. The paper's child percentages use the
**5M–10M interval**. After running all six counter cases, use:

```bash
python3 analysis/extract_auth_metrics.py \
  runtime/paper-experiments/paper/E3/run-report_E3_*_counters.json \
  --start-block 5000000 --end-block 10000000 \
  --output-dir runtime/paper-experiments/paper/E3/auth-metrics-5m-10m
```

Pass `E3/run-report.json` instead of the glob if the whole family was run with
a combined report. New output files are generated by the run; no archive of
the authors' original output is required by this path.

## Fields and formulas

The fixed Geth source already produces these counters:

| Metric | Source | Calculation |
|---|---|---|
| Nil / updated / non-updated child pointers | `additional_node_stats.txt`: `nil` / `dirty` / `clean childs`, `HashedFullNodeNum` | `100 * child_count / (16 * HashedFullNodeNum)` |
| Node writes | Same file: `WrittenTrieNodeNum` | Cumulative end count, or end minus start for a specified window |
| Total node reads | `simBlocks.NodeReadFuncCnt` | Cumulative counter, end minus start for a window |
| Additional reads for myHash | `simBlocks.AdditionalNodeReadFuncCnt` | Cumulative counter, end minus start for a window; do not add this again to total reads |
| State-trie myHash cache hit rate | `ChildReadStateHit`, `ChildReadStateMiss` in `simBlocks` | `100 * hits / (hits + misses)` |
| Storage-trie myHash cache hit rate | `ChildReadStorageHit`, `ChildReadStorageMiss` in `simBlocks` | Same formula |
| Combined myHash cache hit rate | Both state and storage counters | Sum hits and misses first, then calculate the ratio |
| LevelDB data-block cache hit rate | `read_stats`: `CacheHitCounts["data-block"]`, `CacheMissCounts["data-block"]` | `100 * hits / (hits + misses)`; distinct from the myHash cache |
| Total node reads relative to no-myHash | Same-window `NodeReadFuncCnt` of variant and instrumented baseline | `variant_reads / baseline_reads` |

The authentication summary's `Reads / baseline` column
(`node_reads_vs_baseline` in JSON/CSV) reports this **total-node-read ratio**.
The paper's approximately 2.7-fold read ratio uses requests reaching LevelDB,
calculated separately below.

The extractor reads selected `simBlocks` checkpoints without loading the full
multi-GB JSON into Python objects. It parses the small child-stat log and the
required LevelDB read-stat checkpoints separately.

`start-block=0` means cumulative counts through the end checkpoint. With
`--start-block N`, all count differences are taken **before** computing ratios.
The run must contain both child and read-stat snapshots at the requested
boundaries. The standard paper runner saves these snapshots with `simBlocks`
every 500K blocks and at the final endpoint, so both 5M and 10M are available
in a new paper-scale run. The summary remains cumulative by default; request
`--start-block 5000000 --end-block 10000000` for that interval. The extractor
does not silently substitute the cumulative endpoint for a missing boundary
in older runs.

For a child type `C` and hashed branch-node counter `B`, the percentage for
`(start, end]` is `100 * (C_end - C_start) / (16 * (B_end - B_start))`.
This weights all child pointers observed in that interval equally; it is not
an average of checkpoint percentages or a subtraction of two percentages.
The default 0–10M cumulative distribution differs from the paper's 5M–10M
distribution. Read/cache metrics use the same selected window; the node-count
payload estimates below always use the cumulative end count.

The extractor checks the recorded measurement options, endpoint availability,
non-negative counter differences, and the sum of 16 pointers per branch.
It uses integer child counts rather than the rounded percentages printed by
Geth. Zero denominators become JSON `null`, CSV blank, and Markdown `N/A`.
Without an enabled myHash cache there are no cache probes to report; in a
small replay there may also be no reads reaching LevelDB's data-block cache.

## LevelDB read requests for the paper's read ratio

The approximately 2.7-fold read ratio in §5.3.1 compares PV* with myHash and
a unified 4 GiB cache against PV*, using **read requests issued to LevelDB**.
Its source is `read_stats.ReadRequestCount`. For each case, subtract the 5M
counter from the 10M counter, then divide the cache case's count by the
baseline's count. Requests served by Geth's trie caches are outside this
counter; requests served by LevelDB's own caches are included. It is not a
count of physical SSD reads.

After running the whole E3 paper family, extract the interval counts with
the existing storage extractor, then calculate the ratio by case ID:

```bash
./scripts/analyze_storage_metrics.sh \
  runtime/paper-experiments/paper/E3/run-report.json --variant stats \
  --start-block 5000000 --end-block 10000000 \
  --output-dir runtime/paper-experiments/paper/E3/read-requests

python3 - <<'PY'
import csv
from pathlib import Path

path = Path("runtime/paper-experiments/paper/E3/read-requests/read_metrics.csv")
with path.open(newline="") as stream:
    counts = {row["case_id"]: int(row["read_requests"])
              for row in csv.DictReader(stream)}
baseline = counts["E3_PVstar_counters"]
cached = counts["E3_PVstar_myhash_cache4g_counters"]
print(f"PV* LevelDB read requests: {baseline:,}")
print(f"PV* + myHash + cache LevelDB read requests: {cached:,}")
print(f"LevelDB read-request ratio: {cached / baseline:.6f}")
PY
```

The original experiment's 5M–10M counts were 1,952,248,737 for PV* and
5,289,645,899 for PV* with myHash and cache, yielding 2.709514 (about 2.7).
The `read_requests` values in the CSV are already interval differences.

## Arithmetic storage estimates

The output includes three estimates based on `WrittenTrieNodeNum` at the
end checkpoint, even when other counters are reported for a sub-window:

| Output | Calculation in decimal TB | Meaning |
|---|---|---|
| `estimated_hash_payload_tb` | `nodes * 32 / 10^12` | Uncompressed 32-byte hash payload |
| `upper_bound_version4_payload_tb` | `nodes * 16 * 4 / 10^12` | Paper's upper-bound assumption: every node has 16 child-version fields |
| `upper_bound_version2_5_payload_tb` | `nodes * 16 * 2.5 / 10^12` | Same assumption with a 2.5-byte version |

For example, a count of 10.86 billion gives 0.69504 TB and 0.4344 TB for the
last two estimates, explaining the rounded 0.70/0.43 TB values. These are
arithmetic estimates, not measured compressed database sizes.
`WrittenTrieNodeNum` counts trie-node writes, not a census of distinct live
SST entries. The source count and assumptions must accompany the estimate.

## Outputs and verification scope

`auth_metrics.json` records input paths, effective options, measurement window,
the child-log checksum, and numeric metrics. `auth_metrics.csv` contains the
same metric rows. `auth_metrics.md` gives a compact comparison.
Missing baseline reports leave read ratios unavailable and are listed in the
output; supply them to complete the comparison.

The 50K profile checks counter collection and extraction on real transactions.
It does not validate the paper's reported percentages or speedups at 10M.
For each paper claim, match its configuration and measurement interval before
comparing numbers.
